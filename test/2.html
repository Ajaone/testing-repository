01 - Navigation Timing Race Conditions

These tests exploit the gap between when navigation starts and when the address bar updates. The core idea: if we can start a navigation to a trusted URL but control what actually renders, the address bar shows the trusted URL while attacker content is displayed.

Target: Arc Browser iOS & Desktop

A. history.replaceState Race on New Window

Opens a window to the target site. A race between the page loading and our script calling history.replaceState might leave the address bar showing the target URL while we control the history entry. On iOS, the address bar update can lag behind replaceState.

B. location.assign + window.stop() Race

Navigate to target URL then immediately call window.stop() and document.write(). If stop() fires before the address bar updates but after navigation begins, the bar may show the target URL with our content.

C. Double Navigation Race

Fire two navigations in rapid succession. First to attacker page (which renders our content), second to target URL. The address bar may update to show the second URL while the first page's content is still rendered due to the browser's navigation cancellation timing.

D. Anchor Navigation + pushState Interleave

Programmatically click an anchor to target URL while simultaneously calling history.pushState with attacker content. The anchor click triggers address bar update, but pushState may win the content race.

E. about:blank + document.write + replaceState

Open about:blank, write attacker content with document.write, then call history.replaceState with a legitimate URL string. Some browsers update the address bar from replaceState even on about:blank origins.

F. Rapid Window.open + location.replace Loop

Opens a window and rapidly alternates between target URL and attacker URL using location.replace. The rapid oscillation can confuse the address bar's debounce logic, potentially freezing it on the target URL while attacker content is displayed.
