CVE-2026-2378 Bypass — Arc Android

A1. 205 Reset Content (204 variant)

204 was patched. Try 205 Reset Content — same "no body" behavior but different status code. Fix might only check for 204 specifically.

Requires server: /205-reset endpoint

A2. 202 Accepted

202 indicates the request was accepted but not yet processed. Some implementations treat it similarly to 204.

A3. 304 Not Modified

304 tells the browser to use cached content. If there's no cache, the page might stay on the previous URL with empty content.

A4. Hanging response (0-byte body)

Send 200 OK with Content-Length: 0 but keep connection open. Browser thinks page loaded but there's no content to replace the URL bar.

A5. Redirect to same page with fragment

302 redirect back to the SAME URL with a # fragment. Fragment navigation doesn't trigger full page load but may affect omnibar.

B1. intent:// URI Navigation

Android intent:// URIs can trigger app navigation. If the omnibar updates based on intent handling, it might show a spoofed URL during the transition. Similar to iOS geo: scheme bug but Android-specific.

B2. market:// and play store schemes

market:// triggers Play Store. During the handoff between Arc and Play Store, the omnibar state might become inconsistent.

B3. Android deep link race

Navigate to a URL that's also registered as an Android App Link. The disambiguation dialog between browser and app may freeze the omnibar.

C1. pushState + back button race

pushState to google.com, then immediately trigger back navigation. During the back animation, the omnibar might flash the pushState URL.

C2. Multiple pushState then navigate

Push 100 history entries, then navigate to google.com. The history stack overflow might confuse the omnibar's URL tracking.

C3. replaceState during page transition

Start navigation to google.com, then replaceState during beforeunload. The omnibar might show the replaceState URL instead of the destination.

D1. window.open + location.replace race

Open google.com in named window, then rapidly replace with attacker content. The named window reuse might cause the omnibar to keep google.com.

D2. window.open then postMessage navigation

Open a window, then use postMessage to tell the opened page to navigate. Indirect navigation might bypass omnibar update checks.

D3. Popup + close + reopen race

Open google.com, close it, then immediately reopen with attacker content using the same window name. The closed window's URL might persist.

E1. Content-Disposition download interrupt

Navigate to a URL that starts downloading a file (Content-Disposition: attachment). The download dialog might freeze the omnibar on the previous URL.

E2. PDF inline display

Navigate from google.com to a PDF with Content-Disposition: inline. The PDF viewer might display while the omnibar still shows the previous URL.

F1. Redirect loop with limit

20 redirects in a chain (near browser limit). When the browser stops following redirects, the omnibar might show an intermediate URL.

F2. Meta refresh + JS redirect combo

Page with both meta refresh AND JS redirect to different URLs. The competing navigations might confuse the omnibar.

F3. 307 POST redirect to GET

Submit a form via POST, server returns 307 redirect. The method change from POST to GET during redirect might affect omnibar handling.

G1. Scroll-triggered navigation

CVE mentions "after user interaction". What if scrolling triggers the navigation? The omnibar hides on scroll in Arc Android — if we navigate during scroll, the hidden omnibar might update incorrectly.

G2. Pull-to-refresh race

During pull-to-refresh animation, navigate to a different URL. The refresh indicator + navigation might cause the omnibar to show wrong URL.

G3. Touch event + pushState

On touchstart, do pushState to google.com URL. On touchend, navigate away. The omnibar might briefly show google.com during the touch.
