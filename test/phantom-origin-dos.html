Origin Spoofing — Transaction Approval Popup (Critical $12.5k-$20k)

OS-1 — about:blank origin inheritance

window.open("about:blank"), write dApp code, call signTransaction(). Test what origin Phantom shows in the approval popup. If it inherits the opener origin or shows blank, the attacker controls what the user sees.

OS-2 — blob: URI origin in approval

Create blob: URL with dApp code. Phantom may show blob:https://... or just the origin part in approval. Any ambiguity = origin confusion for the user.

OS-3 — history.pushState before signing

Load page, pushState("/app.uniswap.org/swap"), then call connect() + signTransaction(). If Phantom reads origin from webView.url at call time, the path in the popup may show the pushed path, confusing the user.

OS-4 — iframe cross-origin tx request

Load trusted dApp (raydium.io) in visible iframe, attacker page as parent. Test if Phantom's provider in the iframe is accessible from parent, or if the approval popup shows the iframe origin vs parent origin.

OS-5 — Connect as site A, sign from site B

Connect wallet on current page, then navigate to a different origin and check if the wallet session persists. If Phantom doesn't re-validate origin on signing, the approval popup may show stale origin info.

OS-6 — data: URI with Solana provider

Navigate to data:text/html,... containing dApp code. If Phantom injects provider into data: URIs, the origin in the approval popup would be null or missing — user cannot verify what site is requesting the transaction.

OS-7 — srcdoc iframe origin

Iframe with srcdoc containing dApp code. The origin of srcdoc iframes is null but Phantom may display the parent page origin in the approval popup — making it look like the parent site requested the tx.

OS-8 — postMessage provider hijack

Phantom's provider communicates with the native app via postMessage or webkit.messageHandlers. Intercept and replay/modify these messages to spoof the origin field sent to the native approval UI.

Denial of Service — Wallet Crash/Freeze (Medium $1.5k-$5k)

DOS-1 — WebView memory bomb

Rapid allocation of large ArrayBuffers until WebView or Phantom app crashes due to memory pressure. iOS will kill the process.

DOS-2 — Recursive iframe bomb

Each iframe creates another iframe. Exponential growth crashes the WKWebView process.

DOS-3 — Transaction simulation flood

Rapidly fire signTransaction() / signAllTransactions() in a loop. Each call triggers Phantom's native simulation engine + approval UI. Hundreds of simultaneous requests may exhaust the simulation backend or freeze the UI thread.

DOS-4 — Malformed transaction crash

Send transactions with invalid/oversized data to signTransaction(). Malformed instructions, huge memo fields, or impossible account references may crash the transaction parser or simulation engine.

DOS-5 — localStorage / IndexedDB bomb

Fill all available storage. May prevent Phantom from saving state, crash the app on restart, or corrupt cached data.

DOS-6 — Canvas/WebGL OOM

Create massive canvas elements or WebGL contexts. GPU memory exhaustion can crash WKWebView or the entire Phantom app on iOS.

DOS-7 — History API flood

Rapid history.pushState() in a tight loop. WKWebView allocates memory for each entry. Combined with large state objects, this can exhaust memory.

DOS-8 — phantom:// deeplink bomb

Rapid-fire phantom:// scheme navigations via hidden iframes. Each one triggers Phantom's native URL handler. Hundreds in quick succession may freeze the app's main thread.

DOS-9 — signMessage infinite loop

Call signMessage() immediately after user rejects. Creates an infinite approval popup loop that the user cannot escape — every dismiss triggers a new popup.

DOS-10 — WebSocket exhaustion

Open 200+ WebSocket connections to Solana RPC endpoints. Phantom may share the connection pool — exhausting it blocks the wallet from communicating with the chain.
