A3v2 — pending popup URL → Site Settings

A2b already showed Site Settings binds to the false host for an about:// page — but that page is blank, so there is no attacker content under it. This file chases the one thing that changes the severity: can attacker content be on screen while Site Settings names a domain the user never visited?

Four independent routes are tested. Route 1 is the cheap control that gates Route 2. Routes 3–5 do not depend on Route 1 at all — run them even if Route 1 comes back closed.



pwned by 33x




Route 1 · control — does Arc paint a PENDING popup URL?



 
1 · open, observe, touch nothing

 
Opens a popup to a URL whose TCP SYN is blackholed — it hangs 30–75s
 and never commits. The opener then does nothing: no paint, no write, no
 stop(). Read the bar, then also open the menu and read Site Settings,
 then come back.

 
 
 






Route 2 · hanging popup + DOM paint



 
2 · locked — Route 1 must fire first

 
Same hanging navigation, but the opener paints the popup by pure DOM
 mutation (document.title, body.innerHTML,
 appendChild). It never calls
 document.open()/write()/close()/stop() — each of those runs "stop document
 loading", aborts the provisional navigation, and hands Arc the exact teardown event its
 1.48.0 fallback hooks. That is why the earlier nine variants all landed on
 about:blank.

 
 






Route 3 · back-navigation staleness  ★



 
3 · go to about://HOST, then swipe BACK here

 
Independent of Routes 1–2. Navigates this tab to the
 about:// page (Site Settings binds to the false host), then you swipe back so
 this attacker page is on screen again. If Site Settings was cached on commit and is
 not recomputed on a back navigation, you get attacker content + a false host in Site
 Settings — exactly the state that matters.

 
 
Then: swipe back → you should see THIS page → open menu →
 Site Settings → read the host → answer below.

 






Route 4 · cross-tab bleed



 
4 · popup to about://HOST, then return to THIS tab

 
Opens the about:// page in a separate tab, then you switch
 back here without closing it. Tests whether Arc's Site Settings pane is bound to the
 foreground tab or to a shared/last-computed value.

 
 
Then: switch back to THIS tab → menu → Site Settings → answer.

 






Route 5 · opener re-navigates the popup



 
5 · about://HOST first, then swap in real content

 
Opens about://HOST/signin (Site Settings binds to the false host),
 waits, then the opener sets w.location to a real attacker page. Navigating a
 window you opened is permitted even cross-origin, so this should work despite the
 opaque origin. If the bar/Site Settings lag behind the new document, the false host is
 displayed over real rendered content.

 
 






Route 6 · ★★ does the GRANT reach the real domain?



 
6 · highest severity if it fires

 
This one needs no PoC code, only your hands. On the
 about://accounts.google.com/ page, open Site Settings and, if there are
 permission toggles (location / camera / mic / notifications), turn one ON. Then:

 
a. open Arc's global settings → site permissions list. Is there now an entry
 for the real host?

 b. visit the genuine https://accounts.google.com/ and check whether the
 permission is already granted there.

 
If a grant made on the fake page applies to the real domain, that is permission
 injection, not a display bug, and it is a separate report well above Low.
